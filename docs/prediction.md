# 2단계 워크로드 명세와 구현 전 성능 예측

작성: 2026-11-08, 1단계 본측정(`results/phase1`, 커밋 d0ecaa7) 직후, **응용 코드 작성 전**.
이 문서는 태그 `prediction-v1`로 고정한다. 이후 바뀐 예측은 아래 "수정 기록"에 따로 적고 원문은 고치지 않는다.
2인 팀이므로 응용은 pipe와 shared memory(shm) 2가지 버전으로 구현한다 (안내문 2장).

## 1. 응용: 이미지 필터 캐시 서버 (imgcache)
클라이언트가 (이미지 ID, 필터, 매개변수)를 요청하면 서버가 필터를 적용한 이미지를 돌려준다. 같은 요청은 서버 캐시에서 바로 응답한다.
- 이미지: 서버가 ID로부터 결정적으로 만드는 8비트 흑백 이미지 64장. ID 0~31은 128×128(16KB), 32~51은 512×512(256KB), 52~63은 1024×1024(1MB)
- 필터: 반전, 임계값 이진화, 3×3 박스 블러. 매개변수는 임계값·밝기 보정값
- 캐시: (ID, 필터, 매개변수)를 키로 하는 해시맵 + LRU, 용량 64MB

## 2. 워크로드 명세
| 항목 | 값 |
|---|---|
| 요청 메시지 | 64B 고정 (요청 번호, 이미지 ID, 필터, 매개변수) |
| 응답 메시지 | 16B 헤더 + 이미지. 요청 기준 크기 분포: 16KB 50%, 256KB 35%, 1MB 15% (평균 약 255KB) |
| 요청 빈도 | 클라이언트당 미처리 요청 최대 4개(창 4)로 쉬지 않고 보냄 (폐쇄형 부하). 처리량 한계를 재기 위함 |
| 통신 패턴 | N:1 요청, 1:N 응답, 요청-응답. 요청은 작고 응답은 크다 (비대칭) |
| 캐시 적중률 | 두 조건: **적중 80%**(인기 키 24개 중에서 선택), **적중 20%**(나머지는 매번 새 매개변수 → 반드시 미스) |
| 서버 공유 자료구조 읽기/쓰기 | 캐시: 모든 요청이 조회하고(LRU 갱신 때문에 조회도 쓰기), 미스마다 삽입. 작업 큐: 요청마다 넣기 1, 빼기 1. 통계: 스레드별 집계 |
| 동시 클라이언트 | 2, 4, 8 |
| 서버 워커 | 4개 고정 |
| 재현성 | 고정 시드 요청열, 두 버전에 같은 요청열 |
| 측정 | 조건(IPC 2 × 클라이언트 3 × 적중률 2)마다 워밍업 0.5초 후 3초 측정, 30회 반복, 순서는 섞음 |

측정 지표: 요청 지연(클라이언트 요청 스레드가 `ipc_send` 직전에 찍은 시각 → 응답 스레드가 응답 전체를 받은 시각, `CLOCK_MONOTONIC`), 처리량(요청/s, MB/s), 서버·클라이언트 CPU 시간과 컨텍스트 스위치(`getrusage`), 서버 `VmRSS`, 서버의 캐시 잠금 대기 시간과 작업 큐 대기 시간.

## 3. 1단계에서 가져온 근거 (본측정 값)
| 근거 | 1단계 값 |
|---|---|
| 큰 메시지 왕복 지연 p50, 기본 환경 | 256KB: pipe 259.5us, shm 45.5us (클라 1) / 1MB: pipe 1228.3us, shm 115.5us (클라 1), pipe 1931.5us, shm 319.5us (클라 8) |
| 같은 조건, 코어를 깨워 둔 환경 (busy) | 256KB: pipe 62.1us, shm 26.1us / 1MB: pipe 254.3us, shm 144.6us (클라 1) |
| 처리량 중앙값 | 256KB 클라 8: pipe 10355 MB/s, shm 114266 MB/s / 1MB 클라 8: pipe 9005, shm 99049 |
| 1MB 왕복당 클라이언트 자원 (클라 1) | pipe: 자발적 CS 32.4회, sys 441us / shm: CS 1.1회, sys 7.7us, user 93.7us |
| 1MB 왕복당 시스템 콜 (strace, 클라 1) | pipe: read 약 18 + writev 1 / shm: futex 약 147 |
| 작은 메시지 (64B~16KB) | 기본 환경에서 세 IPC 모두 20~50us로 차이 작음, busy에서 2~7us. 코어 유휴 진입이 지연을 지배 |
| 서버 RSS | pipe 1544KB(클라 1) → 1672KB(클라 8) / shm 2696KB → 10008KB. shm은 클라이언트당 약 1MB(채널 양방향 링) 증가 |

## 4. 예측 (구현 전)
| # | 조건 | 예측 | 근거 |
|---|---|---|---|
| P1 | 적중 80%, 클라 2·4·8 | **shm이 pipe보다 요청 지연 p50이 2~4배 낮고, 처리량(MB/s)이 3배 이상 높다** | 응답 평균 255KB, 1단계 256KB~1MB에서 shm 우위. 다만 응용에서는 워커가 일하고 있어 코어가 덜 쉰다. busy 조건의 차이(256KB 2.4배, 1MB 1.8배)와 기본 조건 차이(5.7배, 10.6배) 사이로 본다 |
| P2 | 적중 20% | **두 버전 차이가 크게 줄어 처리량 차이 1.5배 미만** | 미스 요청은 필터 연산(최대 1MB 블러)이 IPC보다 오래 걸릴 것으로 본다. IPC 비용 비중이 작아진다 |
| P3 | 클라 수 증가 (2 → 8) | 두 버전 모두 처리량이 클라 4 근처에서 포화하고, 8에서는 지연이 거의 클라 수에 비례해 늘어난다 | 워커가 4개로 고정. 1단계에서는 서버가 클라이언트마다 스레드를 따로 썼지만 응용은 워커 4개가 나눠 처리 |
| P4 | 서버 메모리 | shm 서버 `VmRSS`가 pipe보다 **클라이언트당 약 1MB 크다** (클라 8에서 약 8MB 차이). 캐시 사용량은 두 버전이 같다 | 1단계 서버 RSS 증가량 |
| P5 | CPU 시간 | pipe는 처리한 MB당 **sys 시간이 shm의 10배 이상**, shm은 user 시간(복사)이 더 크다 | 1단계 1MB: sys 441us 대 7.7us, user 0 대 93.7us |
| P6 | 컨텍스트 스위치 | pipe는 큰 응답 1개마다 수십 번(1MB 약 30회) 잠들고 깬다. shm은 응답당 몇 번 수준 | 1단계 nvcsw/msg |
| P7 | 캐시 잠금 | 잠금 안에서는 조회·LRU 갱신·삽입만 하므로 잠금 대기는 요청 지연의 5% 미만 | 설계: 필터 연산과 전송은 잠금 밖 |

## 5. 예측 확인 방법
- P1·P2·P3: 조건별 30회의 지연 p50/p99와 처리량 중앙값 비교
- P4: 서버 종료 직전 `VmRSS`
- P5·P6: 서버·클라이언트 `getrusage`를 처리 MB로 나눔
- P7: 서버가 잠금 대기 시간을 스레드별로 재서 합산
- 예측이 틀리면 원인으로 추정한 요인만 바꿔 다시 잰다 (예: 워커 수, 송신 잠금 범위, 슬롯 구성)
