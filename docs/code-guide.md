# 코드 가이드

코드를 처음 읽는 팀원을 위한 문서다. 자기 담당 IPC 파일은 끝까지 읽고, 아래 "담당자 확인 질문"에 답할 수 있어야 한다. 발표와 보고서에서 설명해야 하는 내용이다.

## 구조

```
include/ipc.h            세 IPC가 공통으로 지키는 함수 약속
src/transport_pipe.c     FIFO 구현
src/transport_mq.c       POSIX message queue 구현
src/transport_shm.c      POSIX shared memory 구현
src/common.c             시간, 자원 사용량, 검증 패턴
bench/bench_server.c     벤치마크 서버
bench/bench_client.c     벤치마크 클라이언트 (측정 코드)
tests/duplex_test.c      양방향 전송 검증
scripts/                 측정, 검증, 요약 스크립트
```

벤치마크와 나중에 만들 응용은 `ipc.h`의 함수만 호출한다. Makefile이 같은 코드를 세 전송 구현과 각각 링크해 버전별 실행 파일을 만든다.

## 읽는 순서
1. `include/ipc.h`: 함수 약속과 스레드 규칙
2. `src/transport_pipe.c`: 가장 단순한 구현
3. 자기 담당 전송 파일
4. `bench/bench_server.c`의 `worker_main`
5. `bench/bench_client.c`의 `pingpong`, `throughput`

## 한 번의 측정 흐름

```
run_one.sh
 ├─ 서버 실행: 클라이언트별 IPC 자원 생성, 클라이언트마다 스레드 1개
 └─ 클라이언트 실행: 부모가 N개 fork
      ├─ 자식: 버퍼 초기화 → 연결 → 준비 완료 알림 → 시작 신호 대기
      ├─ 부모: 전원 준비되면 시작 신호 (모두 동시에 시작)
      ├─ 자식: 워밍업 → 측정 → 공유 메모리에 결과 저장
      └─ 부모: 끝난 뒤 정렬, 통계 계산, CSV 기록
```

**측정 구간에는 `printf`와 파일 쓰기가 없다.** 지연값은 미리 할당해 페이지를 건드려 둔 배열에 저장하고, CSV는 자식이 끝난 뒤 부모가 쓴다. `fprintf`는 오류로 실행을 중단할 때만 부른다.

## 측정 방식

| 모드 | 시작 | 끝 | 얻는 값 |
|---|---|---|---|
| pingpong | `ipc_send` 직전 | `ipc_recv` 직후 | 메시지별 왕복 지연 |
| throughput | 워밍업 동기화 응답 직후 | 측정 끝 동기화 응답 직후 | 초당 메시지 수, 초당 바이트 수 |

- 왕복 지연은 전송 함수 전체를 재므로 프레임 처리와 조각 나누기 비용이 포함된다.
- 처리량은 끝 동기화 응답까지 재므로 버퍼에 남은 데이터까지 포함된다. 서버가 센 개수와 보낸 개수가 다르면 실패로 처리한다.
- 길이 0 메시지는 제어용이다. 측정 크기는 1바이트 이상이다.

## CSV 항목 (`phase1.csv`)
`role`이 `client`면 클라이언트 1개, `all`이면 그 실행의 합계, `server`면 서버 프로세스다. 시간은 나노초(ns), 처리량은 MB/s(1MB = 10^6바이트)다.

**주의:** 서버의 CPU 시간과 컨텍스트 스위치는 프로세스 전체 구간 값이라 워밍업이 포함된다. 클라이언트 값은 측정 구간만이다. 메시지당 비용 비교에는 클라이언트 값을 쓴다.

## IPC별 구현

| | pipe | message queue | shared memory |
|---|---|---|---|
| 채널 | 클라이언트마다 FIFO 2개 | 클라이언트마다 큐 2개 | 클라이언트마다 세그먼트 1개, 링 2개 |
| 메시지 경계 | 4바이트 길이를 앞에 붙임 | 큐 메시지 단위, 큰 메시지는 조각 | 슬롯의 길이 필드 |
| 조각 단위 | 없음 (바이트 스트림) | 8192바이트 | 8192바이트 |
| 버퍼 크기 (방향별) | 커널 기본 | 5 × 8KiB | 64 × 8KiB = 512KiB |
| 대기 방식 | 커널 파이프 대기 | 커널 큐 대기 | 프로세스 공유 세마포어 |
| 데이터 복사 | 사용자→커널→사용자 | 사용자→커널→사용자 | 사용자→공유 메모리→사용자 |

### 놓치기 쉬운 점
- **pipe:** `PIPE_BUF`를 넘는 쓰기는 다른 쓰기와 섞일 수 있어 클라이언트별로 FIFO를 나눈다. FIFO는 서버와 클라이언트가 같은 순서(req → resp)로 열어야 `open`에서 서로 막히지 않는다.
- **message queue:** 기본 설정에서 메시지 하나는 8192바이트까지다. `mq_receive` 버퍼는 큐의 메시지 크기 이상이어야 해서 마지막 조각은 임시 버퍼로 받는다. 사용자당 큐 메모리 한도(`ulimit -q`) 때문에 클라이언트 8개(큐 16개)에서는 깊이 8부터 생성이 실패했다.
- **shared memory:** 공유 메모리 자체는 동기화를 해 주지 않는다. `spaces`와 `items` 세마포어로 생산자-소비자를 구현한다. 클라이언트가 초기화 도중인 세그먼트를 쓰지 않도록 서버가 마지막에 `magic` 값을 설정한다.
- **자원 정리:** 서버의 시그널 스레드가 `sigwait`로 SIGINT, SIGTERM을 기다렸다가 이름 있는 자원을 지운다. POSIX 자원은 `ipcs`에 나오지 않으므로 `scripts/check_ipc.sh`로 확인한다.

## 스레드 규칙
채널은 전이중이다. 한 방향에 스레드 1개씩이면 잠금 없이 쓸 수 있다. 한 방향을 여러 스레드가 쓰면 조각이 섞이므로 잠금이 필요하다. 2단계 서버의 워커는 클라이언트별 송신 뮤텍스를 잡고 보낸다.

## 검증
`scripts/run_tests.sh`가 다음을 확인한다.
1. 경계 크기(0, 4095, 4096, 8188, 8192, 8193, 65536, 1048577 등) 양방향 전송
2. 클라이언트 1, 2, 8개에서 내용과 순서 검증
3. 측정 중 SIGINT, SIGTERM 후 자원과 프로세스가 남지 않는지
4. SIGKILL 후 `--cleanup-only` 복구
5. 큐 16개 생성
6. ThreadSanitizer, AddressSanitizer

ThreadSanitizer는 프로세스 사이를 보지 못한다. 그래서 `duplex_test`는 한 프로세스 안에서 양쪽을 스레드로 돌린다.

`--verify` 실행은 패턴을 만드는 시간이 들어가므로 측정값으로 쓰지 않는다. `summarize.py`는 이 행을 제외한다.

## 담당자 확인 질문

**pipe 담당**
- 클라이언트마다 FIFO를 따로 둔 이유는?
- `writev`로 헤더와 데이터를 함께 쓰는 이유는?
- 서버가 먼저 끝나면 클라이언트 쓰기에서 무슨 일이 생기는가?

**message queue 담당**
- 1MiB 메시지는 큐 메시지 몇 개가 되는가? (4바이트 헤더 포함)
- 꼬리 조각만 임시 버퍼로 받는 이유는?
- `tmp_tx`와 `tmp_rx`를 하나로 합치면 어떤 경쟁 상태가 생기는가?
- 큐 깊이를 10으로 올리면 클라이언트 8개에서 왜 실패하는가?

**shared memory 담당**
- 세마포어 두 개는 각각 무엇을 세는가? 초기값은?
- `tx_idx`, `rx_idx`를 공유하지 않아도 되는 이유는?
- 이 구현에서 공유 메모리인데도 복사가 2번인 이유는?
- 슬롯을 8 × 64KiB에서 64 × 8KiB로 바꾼 근거는? (`docs/decisions.md`)

**전원**
- 타임스탬프를 왜 그 위치에서 찍었는가?
- `printf`를 측정 구간에 넣으면 무엇이 달라지는가?
- 평균 외에 중앙값과 p99를 왜 보는가?
