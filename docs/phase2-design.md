# 2단계 응용 설계안: 이미지 필터 캐시 서버

**순서:** 1단계 본측정 → 성능 예측 작성과 커밋 → 응용 구현. 예측은 구현 전에 써야 하므로 이 문서에는 예측을 적지 않는다.

## 응용
클라이언트가 이미지 ID와 필터를 요청하면 서버가 처리 결과를 돌려준다. 같은 요청이 다시 오면 캐시에서 바로 응답한다. 이미지는 라이브러리 없이 바이트 배열로 만든다.

주제 조건 점검
- 통신량: 이미지 크기가 16KB~1MB라 IPC 차이가 드러날 수 있다.
- 공유 자료구조: 캐시, 작업 큐, 통계를 여러 스레드가 함께 쓴다.
- 동시 클라이언트: 2개 이상. 단순 중계가 아니다.

## 프로세스와 스레드

**서버**
| 스레드 | 수 | 역할 |
|---|---|---|
| 수신 | 클라이언트당 1 | 요청을 받아 작업 큐에 넣는다 |
| 워커 | 설정값 (기본 4) | 캐시 조회, 필터 연산, 응답 전송 |
| 시그널·통계 | 1 | 종료 처리, 자원 정리, 통계 기록 |

**클라이언트**
| 스레드 | 역할 |
|---|---|
| 요청 | 정해진 워크로드대로 요청 전송 |
| 응답 | 응답 수신, 내용 확인, 지연 기록 |
| 수집 | 측정 끝 판단, 결과 정리 (측정 구간에는 파일을 쓰지 않음) |

## 공유 자원과 동기화 (초안)
| 자원 | 접근 | 기법 | 이유 |
|---|---|---|---|
| 작업 큐 (크기 제한) | 수신 → 워커 | mutex + 조건 변수 2개 | 생산자-소비자, Chap03 |
| 캐시 해시맵 + LRU | 워커 | mutex | 조회 때도 LRU 순서를 바꾸므로 읽기도 쓰기다 |
| 캐시 항목 | 워커 | 참조 카운트 | 전송 중 잠금을 잡지 않고, 전송 중 항목이 삭제되지 않게 한다 |
| 클라이언트별 송신 채널 | 워커 | 클라이언트별 mutex | 조각이 섞이지 않게 한다 |
| 통계 | 전체 | 스레드별 집계 후 종료 때 합산 | 측정 경합을 줄인다 |

## 교착 상태 점검
- 필터 연산과 IPC 전송은 캐시 잠금 밖에서 한다.
- 잠금 순서를 정한다: 캐시 → 항목 참조 증가 후 해제 → 송신 뮤텍스. 두 잠금을 겹쳐 잡지 않는다.
- 클라이언트의 요청과 응답 스레드가 분리되어 있으므로, 양쪽 버퍼가 차도 응답 스레드가 비워 진행된다.
- 작업 큐가 차면 수신 스레드가 멈추고, 이는 클라이언트 전송을 늦추는 역압으로 작동한다. 응답 경로는 막지 않는다.

## 워크로드 변수 (명세 초안)
| 항목 | 값 |
|---|---|
| 이미지 크기 | 16KB, 256KB, 1MB 섞음 |
| 작은 요청 | 요청 메시지 64B 내외, 통계 조회 |
| 통신 패턴 | N:1 요청, 1:N 응답, 요청-응답 |
| 캐시 적중률 | 요청 ID 분포로 조절 (예: 20%, 80%) |
| 동시 클라이언트 | 2, 4, 8 |
| 재현성 | 고정 시드로 세 버전에 같은 요청열 |

구체적인 분포와 요청 빈도는 1단계 본측정 뒤 예측과 함께 확정한다.

## 설계 개선 후보
측정 결과에서 원인이 확인된 것만 적용한다.
- 캐시 잠금 범위 축소, 샤딩
- 전송 묶음 처리
- shared memory에서 복사 횟수 감소
- message queue 조각 크기 조정 (커널 한도 안에서)
- 캐시 용량 제한으로 메모리 사용량 절감
